# katzen-airgapped: repository review (2026-10-30)

## Verdict

**Not a finished product.** The current code can exercise local QR framing, a protected local mailbox, and synthetic packet handling. It cannot deliver an offline-generated packet over the live Katzenpost mixnet. Calling it production-ready would be inaccurate. No P2P transport is part of this project.

## System boundary

The cold device holds user plaintext and private state. The hot device scans QR or removable-media data and may contact `kpclientd`. Both optical and file imports are untrusted inputs. A physical air gap must be established outside the application. The hot device must never receive a cold-side decryption key or plaintext by default.

## Findings

| Severity | Evidence | Effect | State |
|---|---|---|---|
| Critical | `src/sphinx.rs` uses a custom 1024-byte packet and synthetic PKI; `src/main.rs`, `src/cold_main.rs` and `src/ui.rs` generate it | No protocol-compatible live delivery or anonymity claim is justified | Live dispatch remains disabled; authentic PKI and protocol implementation required |
| Critical | The original synthetic topology derived private node keys from the public epoch | Anyone could reconstruct demonstration keys | Changed to OS-random keys; old demo artifacts are unsuitable for secrecy |
| Critical | `SurbPackage` exported `k_surb_hex` in its QR JSON | The hot device could learn the reply decryption secret | Removed from exported package; durable cold-side reply state still missing |
| High | `src/lib.rs` accepted unbounded QR sequences and unchecked part metadata; `src/thinclient.rs` accepted recursive CBOR without depth or item limits | Malformed input could exhaust memory or stack | Added bounds and regression tests; fuzzing remains required |
| High | `src/thinclient.rs` accepted arbitrary TCP daemon destinations | Sensitive protocol requests could be sent to an unintended remote endpoint | TCP restricted to numeric loopback addresses; Unix sockets remain preferred |
| High | `SphinxEngine::build_packet` silently truncated message and destination | Data loss and misrouting | Rejects over-capacity input |
| High | `src/pigeonhole.rs` has a demonstration BLAKE3 tag that cannot be verified from an X25519 box ID | No authenticated sender identity | `verify_signature` rejects; replace with actual protocol identity and signature |
| High | Legacy mailbox JSON and prior plaintext inbox files may remain on disk | Existing secrets may be exposed at rest | Mailbox permissions restricted; first unlock migrates mailbox; old copies require separate handling |
| High | `src/ui.rs` relies on terminal passphrase entry and has no validated recovery or backup flow | Desktop UX and recovery are incomplete | Release blocker |
| Medium | `src/thinclient.rs` implements custom CBOR and daemon RPC without a live compatibility test | Framing, parsing, or request semantics may differ from current daemon | Bounded parser; replace with maintained thin-client binding where feasible and test with a controlled daemon |
| Medium | QR checksum is only a four-byte unkeyed integrity check | An active scanner/input can change frames | Treat QR content as untrusted; authenticate application messages before accepting them |
| Medium | No two-device, restart, adversarial input, or live network test has passed | Delivery and isolation properties are unproven | See `SECURITY_TEST_PLAN.md` |

## Release gates

1. Specify the offline/online wire contract against current Katzenpost specifications and the Rust thin-client API. Remove the synthetic Sphinx/BACAP path from any user-facing delivery flow.
2. Implement verified identities, authenticated PKI import, monotonic epoch checks, replay rejection, reply key persistence, and durable encrypted queues.
3. Add a usable GUI unlock and recovery flow, safe migration of existing files, and clear error handling for failed writes.
4. Pass parser fuzzing, malformed-frame and failure-injection tests, two-device physical isolation tests, and live end-to-end send/reply tests with a controlled network.
5. Review privacy and anonymity claims against observable timing, volume, retries, and compromised relays. Obtain an independent security review before a production claim.

Passing unit tests proves only the local invariants covered by those tests. It does not prove air-gap, anonymity, interoperability, or production readiness.
